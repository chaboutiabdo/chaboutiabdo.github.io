One function, four modes: the AI inside THE SMART

THE SMART has four AI features. They all go through one server function — and that single decision is what makes them affordable, safe and debuggable.

Why one door

It’s tempting to call an AI API from wherever you need it. That’s how keys end up in the browser and costs become a mystery. In THE SMART, every AI call — tutor, mistake explanations, flashcards, exam solving — goes to a single Supabase Edge Function, gemini-chat. The client sends a mode; the function decides everything else. The browser never talks to Gemini, and the key never leaves the server.

That one door gives me one place to:

  • Check who’s asking. The session and the premium check run before the mode switch, so they cover all four features at once.
  • Count. 60 calls per student over a rolling 24 hours — no midnight reset to game.
  • Cap inputs. 4,000 characters per question, the last 6 turns of context, 10 MB per PDF, 64 KB per request body.
  • Log to the database, not to server logs. Questions go to ai_learning_conversations; their text is deliberately kept out of the function’s logs.

The four modes

Tutor. A multi-turn chat in Arabic, tied to one subject and one chapter. Both come from a closed list in src/lib/bac.ts, so no free text reaches the system prompt through them — no prompt injection by picking a “subject”. It answers the way a BAC paper is written: an Arabic explanation, Latin notation, step by step.

Explain my mistake. The student opens a question they got wrong. The server loads it by id and checks ownership itself — the function runs with the service key, which bypasses row-level security, so that check is not optional. A missing id and someone else’s id both return 404, so nobody can probe which ids exist. The explanation is saved: reopening it is free, and reading it schedules the mistake for review three days later.

Flashcards. Gemini’s JSON mode with a schema, so the answer is data, not prose. 5–10 cards per chapter, de-duplicated against the student’s deck and within the batch. If one card is malformed, the whole batch is rejected — half a deck is worse than none.

Exam solver. The only multimodal call: the paper’s PDF is sent to Gemini as a native attachment. If the official solution exists, the model explains it; if not, it solves from scratch — and the page tells the student which one they’re reading (grounded or derived).

Cost is the design

The key runs on Gemini’s free tier, so cost control isn’t a detail — it’s the architecture.

  • Solve once, share forever. Exam solutions are cached by (exam_id, prompt_version) and shared by every student, so each paper is paid for once in the life of the app. A prewarm script (npm run prewarm:solutions) solves every paper ahead of time, so students get cached answers instantly.
  • Charge before, not after. The solver records its quota before calling the model. Otherwise a generation that keeps failing turns into unlimited free calls.
  • Version the prompt, not the cache. When the solving prompt improves, SOLVE_PROMPT_VERSION goes up and old answers simply stop matching.
  • No read policy on the shared cache. Students can’t query the solutions table directly; only the function can.

When Gemini is busy

Free-tier models get rate-limited and overloaded. The function holds a chain of five Gemini models. On a 429, a 503 or a timeout it moves on to the next one — without retrying the same model, because a model that just said “busy” is still busy. Exam solving uses its own quality-first chain with a longer timeout.

// simplified
for (const model of MODELS) {
  try {
    return await callGemini(model, request, { timeoutMs });
  } catch (err) {
    if (isBusyOrTimeout(err)) continue;   // 429, 503, timeout → next model
    throw err;
  }
}
return busy(503);  // every model busy: "try again in a moment"

Guarding the one door

One door is also one place to attack, so it gets the guards:

  • An SSRF guard on paper URLs: https only; no localhost, ::1, private ranges or 169.254.* (cloud metadata); and redirect: 'error', so an allowed URL can’t bounce to a forbidden one. The logs show it rejecting 169.254.169.254 for real.
  • An attack suite that calls the function as real users: the daily ceiling, oversized papers, SSRF, forged and anonymous premium requests. More on that in I attacked my own app 210 times.

If you’re building the same thing

  1. Put every model call behind one server function. Your key, your quota and your logs live there.
  2. Cache anything that doesn’t depend on the user. For us, that’s most of the cost.
  3. Make the model return data — JSON with a schema — whenever the UI needs structure.
  4. Expect the model to be busy. Have a fallback chain and a friendly “try again”.
