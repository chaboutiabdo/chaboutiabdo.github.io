One meal, one credit: RFID meal cards on Odoo 19

During my internship at Groupe HIS-HTC-IRA I built the university’s prepaid meal system on Odoo 19. The whole system serves one rule: one meal served = one credit consumed.

The shape

Two points of sale:

  • The Student Centre sells meal plans — weekly, monthly, semester — for real money.
  • The University Restaurant serves meals; each meal spends exactly one credit.

Students tap an RFID card. The card carries an identifier and nothing else — every credit lives in the database. Lose your card and you lose nothing: block it, issue a new one, balance intact.

res.partner ──> his.meal.card ──> his.meal.subscription ──> his.meal.transaction
 the person      names them,       one purchase: credits     one line per credit
 owns balance    holds no credit    + validity window         that moved, forever

A meal plan is an ordinary Odoo product with two extra fields, meal_credits and meal_validity_days. Pricing, payment, invoicing and POS sellability all come for free, and there’s no parallel “plan” model to keep in sync.

Where credits move

Exactly one place: pos.order._apply_meal_credits(), on the server, when a validated order is saved.

  • A line whose product carries credits → grants a subscription.
  • The restaurant’s meal product priced at zero → spends one credit per unit.
  • The same product at its real price → a paying walk-in; no balance is touched.

The POS button that shows a balance is a convenience. A cashier with the browser console open can’t grant a credit or serve an unpaid meal — the order simply fails to validate. Credits are taken one at a time from the soonest-to-expire subscription, so credits close to expiry are always used first.

Four guarantees, independent on purpose

Defeating one doesn’t defeat the others.

GuaranteeMechanism
The server decides_apply_meal_credits, not the browser
No negative balanceCHECK (credits_used >= 0 AND credits_used <= credits_total) in Postgres
Two tills can’t both spend the last creditSELECT … FOR UPDATE on the person’s subscriptions before reading
Nothing changes silentlythe ledger’s write() and unlink() always raise — for admins too

And credits move exactly once per order: before applying anything, the code looks for a ledger line carrying that order’s id, so an order that syncs twice can’t charge twice. When a correction is genuinely needed, there’s one sanctioned path — an adjustment wizard that writes its own ledger line, with a name on it.

The RFID reader is a keyboard

The reader types the card’s 10-digit UID and presses Enter. That’s convenient — no driver, works with any till — and dangerous: the POS has to tell a card scan apart from a product barcode. That part got its own section in the handover document, because it’s the first thing a well-meaning developer would “clean up” into a bug.

Proven on hardware

43 automated tests, green — and then the real thing: real cards on a real RFID reader, end to end. Later versions added two meal tiers with half credits, a working-day view, and an advance of two meals on an empty card.

What I took from it

It’s the same lesson as THE SMART’s leaderboard exploit: anything with a value is decided by the server and protected by the database. The UI is for humans; the rules live below it.

And one more: write down what looks wrong but is deliberate. The handover file for this module marks every one of those with a ⚠ — because the next person to open the code, human or AI, will want to “fix” them.
