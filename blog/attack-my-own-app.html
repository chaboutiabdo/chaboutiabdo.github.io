I attacked my own app 210 times

THE SMART has a leaderboard, premium features and a paid AI. That makes it worth cheating. So before launch I wrote an attack suite that tries — as real, signed-in users.

The setup

npm run seed:testusers creates 55 accounts: 40 students, 10 premium students and 5 admins. Then npm run security runs two suites against the local Supabase stack:

  • check-security.mjs — the five original row-level-security assertions
  • attack-suite.mjs — 205 attacks, each run by a real signed-in user with a real session token

Every test passes when the attack is blocked. What it tries:

  • Privilege escalation — a student changing their own role, subscription status or score
  • IDOR across the 55-user cohort — reading or editing another student’s data by id
  • Points and score forgery, and download-counter forgery
  • An anonymous read sweep over every table
  • Premium bypass, storage access, private flashcard decks and per-student AI caches
  • The AI function — the daily ceiling, oversized papers, SSRF, forged and anonymous premium requests

The bug that justified all of it

The leaderboard reads profiles.total_score. At one point, three different formulas competed to write that column — and two of them read tables a student could write to. So a single insert from the browser console set your leaderboard score to any number you liked:

// illustrative
await supabase.from('quiz_attempts').insert({ quiz_id, score: 999999 });

And a perfect retake re-banked its score every single time.

The fix: one writer

  • Grading moved into Postgres. submit_quiz_attempt is the only thing allowed to write a score. The browser reads quizzes_public, a view that strips the answer key — so the key never reaches the client at all.
  • Open, but don’t score. A student may create an attempt, but the insert policy pins score = 0, completed_at IS NULL and submitted = false.
  • One writer for the total. profiles.total_score is written only by update_student_total_score, which sums points_transactions.
  • Points only from the server. They enter only through SECURITY DEFINER functions, and the award RPC is revoked from authenticated — a browser can’t even call it.
  • Every award is idempotent. A unique index means the same points can’t be banked twice:
-- simplified
create unique index on points_transactions
  (student_id, source_type, source_id, coalesce(question_id, ''));

A trap inside the fix

The trigger that recomputes the total runs AFTER INSERT OR DELETE. On a delete, NEW is null — so anything it reads must use COALESCE(NEW.x, OLD.x). Get that wrong and the delete path raises, the trigger’s own EXCEPTION block swallows the error, and scores silently go stale. No crash, no log you’ll notice — just a wrong leaderboard. It’s written in the project’s invariants now, so nobody “simplifies” it back.

Rules I keep

  1. Reseed before every run. A failing run can leave escalated roles behind, and stale roles make later tests pass for the wrong reason.
  2. Test as a user, never as an admin. The service key bypasses row-level security. Your tests shouldn’t.
  3. Anything with a value is written by the server. Scores, points, credits, roles.
  4. Keep the suite in the repo and run it after every migration.

I later applied the same rule — the server decides — to a university’s meal-credit system on Odoo. Different stack, same lesson: One meal, one credit.
